# REVIEW 항목 처리: $ARGUMENTS

대상은 `docs/REVIEW.md` 의 "$ARGUMENTS" 번 항목이다. 번호가 비어 있으면 미처리(`[ ]`) 항목 중 가장 앞의 차단·결함 항목을 고르고, 그렇게 골랐다고 말한다.

현재 브랜치: !`git branch --show-current`
작업 트리: !`git status --short | head -20`

## 1. 읽고 설명하기 (코드를 고치기 전)

1. REVIEW.md 에서 해당 항목의 위치 / 증상 / 원인 / 수정 방향 / 완료 기준을 읽는다. 언급된 파일을 연다.
2. 사용자에게 **배경 → 선택지와 장단점 → 추천** 을 쉬운 말로 설명한다. 사용자는 백엔드 입문자라서 선택지만 던지면 고를 수 없다. 새 용어에는 한 줄 정의를 붙인다.
3. 다음 중 하나면 설명 뒤 **사용자 답을 기다린다**: 설계·구조 결정, 환경 값(포트·계정·비밀) 변경, 1~2단계 학습 영역(`src/floors/**`, `prisma/schema.prisma`) 수정. 그 외 명확한 결함 수정은 "추천안대로 진행한다" 고 말하고 바로 진행한다.

## 2. 브랜치

작업 트리가 깨끗한지 확인한 뒤 최신 main 에서 만든다. 열린 PR 브랜치 위에 쌓지 않는다.

```bash
git fetch origin && git switch -c <type>/<주제> origin/main
```

type 은 fix / docs / chore / feat 중 하나. 주제는 영어 소문자와 하이픈.

## 3. 구현과 커밋

- 변경 하나당 커밋 하나. 메시지는 `type(범위): 한국어 설명`, 본문에 이유, 끝에 `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.
- 주석 수정, 코드 수정, 문서 수정은 커밋을 나눈다.
- 커밋 전 훅이 비밀 정보와 타입 검사를 한다. 막히면 원인을 고친 뒤 다시 커밋한다.

## 4. 검증

- `/verify` 절차를 그대로 따른다 (타입 검사, 포맷, 컨테이너, 헬스체크).
- 항목의 "완료 기준" 을 실제로 재현해 확인한다. 가능하면 **고치기 전 실패를 먼저 재현**하고 고친 뒤 통과를 확인한다. 재현 스크립트는 저장소가 아니라 스크래치패드에 둔다.
- 검증용 산출물(마이그레이션, dist, 로그, 임시 .env 값)은 되돌린다.

## 5. REVIEW.md 기록

요약의 체크박스를 `[x]` 로 바꾸고, 상세의 `처리:` 줄에 `YYYY-MM-DD · 브랜치/커밋 · 확인한 것` 을 적는다. 별도 커밋 `docs(review): N번 처리 기록`.

## 6. 푸시와 PR

```bash
git push -u origin <branch>
gh pr create --title "<type>: <제목>" --body-file <스크래치패드의 본문 파일>
```

본문 구성: 배경(REVIEW N번) / 변경 / 확인한 것(표) / 남은 것 / 끝줄 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.

## 7. 보고

PR 링크, 커밋 목록, 검증 표, 사용자가 다음에 할 일(병합 후 실행할 명령), 새로 나온 용어 후보를 한국어로 정리한다. 병합은 사용자가 한다.
